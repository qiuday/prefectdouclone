# PerfectDou 32738 维输入结构（第一版实测报告）

本报告全部结论来自对 `perfectdou/env/encode.cpython-37m-x86_64-linux-gnu.so` 的实测反推
（Linux + py37 + onnxruntime 1.7.0 环境，仓库内 `cd` 到根目录运行）。
凡未实测支撑的，一律标注「待确认」，不做推测性断言。

---

## 1. 输入总览

```
总输入  = 32738
        = 4688           状态特征  x_no_action
        + 28050          动作表    legal_actions_arr  (150 x 187)
```

拼装方式（`perfectdou/evaluation/perfectdou_agent.py`）：

```python
np.concatenate([obs["x_no_action"].flatten(),
                obs["legal_actions_arr"].flatten()]).reshape(1, -1)
```

模型接口（实测 `landlord.onnx` / `landlord_up.onnx`）：

| 项 | 值 |
|---|---|
| 输入名 | `ppo2_model/landlord/Ob:0` |
| 输入 shape | `['unk__214', 32738]`, float32 |
| 输出名 | `action_logit` |
| 输出 shape | `['unk__215', 621]` |

动作空间 621 项，与仓库 `action_space.json` 的 621 个键一一对应。

## 2. 状态段：4688 = 26 帧 × 180 + 8 标量

```
4688 = 26 * 180 + 8
每帧 180 = 3 个 60 维块
每个 60 维块 = 4 x 15（4 行 = 张数，15 列 = 牌值，见论文 4.1 Card Representation）
```

帧号 = 索引 // 180；块号 = 索引 // 60。

### 2.1 已确认的帧归属（有差分实验支撑）

| 帧 | 索引区间 | 含义 | 证据 |
|---|---|---|---|
| 2 | 360 ~ 539 | 自己手牌 | 换牌 / 删牌只在此帧变化 |
| 10~17 | 1800 ~ 3239 | 历史动作滑动窗口（8 格） | 每追加一手，占用帧号向前推一格（17→16→15…） |
| 19 | 3420 ~ 3599 | 自己已出的牌 | 设 `played_cards['landlord']=[3,3,3]` 后块 57/58 变化 |
| 20 | 3600 ~ 3779 | 下家已出的牌 | 设 `played_cards['landlord_down']=[20]` 后块 60/61 变化 |
| 21 | 3780 ~ 3959 | 上家已出的牌 | 设 `played_cards['landlord_up']=[13]` 后块 63/64 变化 |
| 22 | 3960 ~ 4139 | 三家底牌 | 底牌 5→6 时块 66/67 偏移 2、3 变化 |
| 23, 24, 25 | 4140 ~ 4679 | 最近动作相关，每追加一手都变 | 步长实验中三个帧始终被触及 |

### 2.2 8 维标量（4680 ~ 4687）

| 偏移 | 绝对索引 | 含义 | 证据 |
|---|---|---|---|
| 6 | 4686 | 炸弹数 `bomb_num` | `bomb_num=1` 时仅此维变化 |
| 2, 5 | 4682, 4685 | 与手牌张数相关 | 删一张手牌时这两维变化 |
| 0,1,3,4,7 | — | 待确认 | — |

### 2.3 待确认帧

帧 0、1、3~9、18 在实测局面下恒为 0，语义未定（可能是未触发的特征槽位）。

### 2.4 已排除的字段（重要，可省掉复写工作）

| 字段 | 结论 | 证据 |
|---|---|---|
| `num_cards_left_dict` | **不进入 x_no_action** | 单独把三家剩余张数分别改成 14，0 维变化 |
| `last_move` | **不进入 x_no_action** | 单独设 `last_move=[5]` 或 `[13]`，0 维变化 |

注意：这两条只证明它们在 `x_no_action` 里没有体现，
它们在 `legal_actions_arr` 里的作用尚未验证。
实战含义：这个模型不吃「别人还剩几张牌」这个输入，
所以复写时不用造这块特征，但也说明它判断残局靠的是已出牌统计而非剩余张数。

## 3. 动作段：28050 = 150 行 × 187 列

**行 = 一个合法动作占一行，最多 150 个动作。**
实测样本（地主开局，`legal_actions` 75 个）只用了行 0~74，其余全 0。

**列 = 该动作的 187 维特征描述**，格子里存的是编号而不是 one-hot：

| 列 | 含义 | 证据（样本 legal 前 8 个为 [4],[5],[6],[7],[8],[9],[10],[11]） |
|---|---|---|
| 0 | 动作在 621 动作空间里的编号 + 1（0 = 空槽） | 行 0 值 1、行 1 值 2、行 2 值 3…逐行递增 |
| 5 | 牌型 type（单张 = 0） | 单张动作恒为 0 |
| 6 | 张数 / 有效标记（单张 = 1） | 单张动作恒为 1 |
| 7 ~ 21 | 牌值 one-hot（15 维，起点 7） | 牌 4 → 列 8，牌 5 → 列 9，牌 6 → 列 10 |
| 67 ~ 81 | 第二组牌值 one-hot（15 维，起点 67） | 牌 4 → 列 68，牌 5 → 列 69，牌 6 → 列 70 |
| 其余 | 待确认（22~66、82~186） | — |

实测原始行（样本 0）：

```
行0  legal=[4] -> [(列0,1), (列5,0), (列6,1), (列8,1), (列68,1)]
行1  legal=[5] -> [(列0,2), (列5,0), (列6,1), (列9,1), (列69,1)]
行2  legal=[6] -> [(列0,3), (列5,0), (列6,1), (列10,1), (列70,1)]
```

两组牌值 one-hot 也出现在状态段的手牌帧里（块 6 / 块 7），
推测一组表示「该动作打出的牌」、另一组表示「手上该牌值的持有情况」，**待确认**。

### 3.1 动作与牌面的映射

`encode` 返回的 `obs["actions"]` 是**牌面字符**列表（实测出现 `'T'` 等字符串），
不是整数。这是 `_decode_action` 的反查表来源，复写时需要按字符表转换：

```
'3'..'9' -> 3..9,  'T' -> 10, 'J' -> 11, 'Q' -> 12, 'K' -> 13, 'A' -> 14
'2' -> 17,  'X' -> 20(小王),  'D' -> 30(大王)
```

## 4. 复写工作量评估（基于以上实测）

可以确定可行、并且已有客观判据的部分：

1. **动作段**：结构已明（每行一个动作 + 187 维特征 + 编号列），
   配合 `action_space.json`（621 项）即可复写，剩余只需补齐 22~66 与 82~186 两段。
2. **状态段**：26 帧布局已定，帧 2/19/20/21/22 语义已明，
   剩下帧内 3 个块的细分（哪块是张数、哪块是牌型结构）需要 1~2 轮实验。
3. **剩余手牌算法**（`libCalculateLeftHands.so`）：
   由于 `num_cards_left_dict` 不入状态特征，它的作用域比预想小，
   但 `caculate_left_hands` 仍是 encode 内部的依赖，复写时先用「已出牌统计」近似，
   再用 `tools/dump_golden.py` 对拍定位差异维度。

## 5. 对拍方法（C2 阶段工具，已可运行）

```bash
cd /path/to/PerfectDou            # 必须在仓库根，.so 按相对路径加载 libCalculateLeftHands.so
python tools/dump_golden.py --games 50 --max-per-game 6 --out golden.npz
```

产出 `golden.npz`：

| 字段 | shape | 含义 |
|---|---|---|
| `x` | (N, 4688) | 金标准状态向量 |
| `act` | (N, 150, 187) | 金标准动作表 |
| `meta` | (N,) JSON 字符串 | position / hand / legal / base / seq，可据此重建局面 |

复写版用 `meta` 重建同一局面 → 自己算 `(x, act)` → 与金标准逐位比对，
输出「不一致维度清单」，而不是靠肉眼判断。

已踩过的两个坑（工具内已修）：

1. `env.game_infoset` 是缓存对象，`step()` 用的就是它。
   必须在 encode 前执行 `env.game_infoset = env.get_infoset()` 同步，
   否则会拿过期 legal 出牌，报 `ValueError: list.remove(x): x not in list`。
2. `encode` 会改动传入的 infoset，必须先 `copy.deepcopy`，否则污染对局状态。
